# 通用 Skill 的结构与协作思路

## 核心思路

通用包保留工作方法、模块分工、输入格式、空白资料模板和校验规则。公司、品牌、商品、类目、报价、资质、工厂、客户与案例等具体事实在初始包中都不预填，由使用者提供资料后再建立自己的配置。

平台固定为阿里巴巴国际站。这里的“通用”是更换公司和产品类目时复用同一套工作方法，不是直接复制上一家公司的数据。

## 整体结构

```text
共同入口：一次性资料文件夹＋完整准备清单
                 ↓
统一读取与核对：页面结构 ↔ 产品事实 ↔ 公司能力
                 ↓
集中反馈缺项和冲突 → 用户确认 → 公司专属参考库
                 ↓
        ┌────────┴─────────┐
        ↓                  ↓
   上品主控             商品视觉 Skill
   ·属性与交易字段       ·品牌与素材配置
   ·标题子模块           ·主图与详情页规划
   ·卖点子模块           ·制作和逐图复核
   ·资料及字段校验       ·成品图片交接
        └────────┬─────────┘
                 ↓
字段计划＋图片清单＋来源＋待处理项
                 ↓
真实页面填写／上传／授权保存／回读
                 ↓
明确授权后正式发布并核验最终状态
```

最后的真实页面执行是目标链路，当前通用执行器尚未完整迁移，不能把流程图当成已经全部实现。

## 主控、sub skill 和辅助工具怎样分工

| 组成 | 职责 | 交给下游什么 |
| --- | --- | --- |
| 上品主控 | 识别当前公司与产品、安排顺序、汇总缺口和结果 | 同一份确认资料、当前类目规则、待处理清单 |
| 标题 sub skill | 根据确认资料组织标题候选并检查一致性 | 候选、推荐理由、来源和疑点 |
| 卖点 sub skill | 从真实产品与公司能力提炼采购信息 | 文案草稿及逐项证据，不为凑数补事实 |
| 商品视觉 Skill | 根据真实素材与确认要求规划和制作图片 | 成品文件、用途、来源和复核状态 |
| 参考资料 | 保存公司配置与类目结构，让同公司后续复用 | 有来源和版本的规则；不是独立执行器 |
| 本地辅助脚本 | 检查基础证据标记、字段计划、图片文件及映射 | 本地复核结果，不直接证明页面已操作 |

子模块不各自重新向使用者问一套资料。主控统一收集，再把与当前子任务有关的确认资料传过去，输出后统一检查。

## 一次收集，内部按依赖核对

使用者取得空白文件夹后，一次放入已有资料：产品类目、选类目后的发布页 URL／截图、公司介绍、产品资料、交易物流、品牌与可用素材。没有的标待补，不适用或不可公开的说明范围。平台和市场不重复询问。

Agent先统一读取，不看一个文件就追问一次。内部按以下顺序处理：

1. 发布页说明平台有哪些字段、必填项、单位、下拉选项和图片模块。
2. 产品资料说明当前产品的真实值；公司资料说明可使用的主体与业务能力。
3. 将字段和资料逐项对应，列出已取得、缺少、冲突和不适用内容。
4. 缺口集中反馈成一张表，用户确认摘要后保存配置。

可以直接读取获授权的当前页面时，由Agent观察；无法读取时由使用者提供分区截图、展开属性及下拉搜索结果。只见默认几项选项，不能当作完整列表。

## 参考库怎样保持可换公司、可换类目

```text
references/
├── companies/<公司标识>/     使用后才创建
│   ├── company.md           当前公司的确认事实
│   ├── category-rules.md    引用当前类目规则与版本
│   ├── business-rules.md    适用的业务与交易条件
│   ├── visual-guide.md      该公司的视觉与素材要求
│   ├── sources.md           来源、版本与授权
│   ├── readiness.md         可以开展什么、仍缺什么
│   └── products/<产品标识>.md
└── categories/<类目标识>/    核实页面后才创建
    ├── category.md
    ├── fields.json
    └── evidence.md
```

两层不能混：类目结构不预填某个公司的品牌、产能、认证或价格；公司资料不自动证明每个产品的参数。每个产品绑定自己的标识和来源，换公司新建专属目录，换类目重新核对页面结构。

确认后的公司资料留在自己的授权环境。再次分享通用包时只带空白模板与方法规则，不夹带公司参考库、具体类目配置、成品或演练材料。

## 内容和图片怎样汇合

属性、交易数据、标题和卖点使用同一产品的确认资料。已有标题、关键词和参考稿选填；没有也可生成草稿，但产品事实不足时先列缺口。

视觉分支使用真实产品素材与已确认要求，参考图不当成实物。缺少证据的资质、工厂、客户或评价模块不启用。原图、草稿与确认成品分开存放。

交接时每款产品独立目录：主图用 m1.png 起的本地规范名称，详情图用 d1.png 起的名称；由明确的模块映射清单决定详情用途和顺序，不能只凭文件名猜当前页面模块。图量、尺寸与上传限制仍核对实际页面。

两条分支汇合后，主控同时核对文案、参数、图片和交易信息是否同款、同版本、同依据，再准备真实页面实验。

## 缺资料和选填怎样处理

- 基础身份、产品事实与页面结构不足：暂停依赖它的部分，集中说明需要补什么。
- 选填参考没有：不阻断不依赖它的工作，不让使用者先写成品文案。
- 页面实际必填值缺失：不能用默认值、近似选项或另一产品的值凑齐。
- 证明或素材没有：关闭对应展示模块，不生成虚假的公司或产品事实。
- 来源冲突：保留冲突与适用版本，确认前不自动升级为可填写数据。

## 如何区分“资料准备好”和“真的上架成功”

当前已有通用Agent规则、资料模板和本地检查工具，也做过独立本地审查。它们帮助发现输入、字段与文件问题，不验证所有来源真实性，也不代替实际看图。

真实页面填写、图片上传、草稿保存和保存后回读尚需针对具体类目适配与验证；完整视觉模板和批量制作也未完成通用迁移。只有实际页面最终状态能证明上传、保存或发布。本地ready和一份写好的参考文件不能替代它。

这份说明用于讲清体系结构、资料流与协作逻辑；具体资料准备和文件命名细则另见相应参考说明。
